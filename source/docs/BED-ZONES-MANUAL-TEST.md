# Bed zones: manual test guide

What the unit tests cannot prove: the real board, the real heaters, DSF's interception and the page in a browser. Run this with the machine
idle and someone next to it. Nothing here needs a part to be printed until test 10.

Code: `dsf/bed_zones.py` (the logic), `bed_zones_config.py`, `bed_zones_intercept.py`, `bed_zones_ops.py`, `bed_zones_mirror.py` (this repo);
the section "Bed zones" of Printing and the backup macro `bedzones-set.g` (TallerPlugins). API: `docs/api/README.md`, "Bed zones".

## 0. Who decides what

| Piece | What it decides | What it never does |
|---|---|---|
| **The firmware (RRF, the Duet)** | The PID of every heater, its M143 maximum, the heater fault and sensor fault detection, what happens on an error, the power of each output. It keeps doing all of it with the service stopped, crashed or killed. | Nothing here depends on the service. |
| **WorkshopService (the brain of this feature)** | How a temperature is split across the zones: which beds are zones, their offsets, the maximum it accepts, the tolerance and timeout of M190. It owns the settings. | It has no control loop: it only sends `M140 P<bed> S<temperature>`. It never raises a limit of the firmware, never turns a protection off, never writes a heater parameter. |
| **`bedzones.g` on the board** | Nothing. It is a copy of the settings that the service writes (at every save and at start) so the backup macro can read them. | It is never edited by hand and never overrides the service. |
| **`bedzones-set.g` (backup macro)** | Nothing of its own: it does what the service would do, from that copy. | It refuses at or over the M143 limit of a heater, whatever the settings say. |

If a test below makes you doubt that the firmware is still in charge, stop and turn the heaters off ("Turn all off" of test 4, the backup macro of test 9, or the power).

## 1. Before you start

- [ ] The machine is idle, cold, in FFF mode, nobody is printing. Someone is at the machine from test 4 on.
- [ ] You can sign in as **technician** (settings) and **administrator** (to see everything); also an operator and, if the machine has users, a viewer.
- [ ] Start with LOW limits: in the settings put **maximum temperature 60** and **timeout 120** until tests 1 to 9 pass. Raise them only after.
- [ ] Open the service log (`workshop-service.log` in the service folder) and `journalctl -u duetcontrolserver -f` in a second window.
- [ ] Know where the power switch is. Know which bed is physically which zone (label them before testing: bed 0 = front left, and so on).
- [ ] The installed versions are the ones to test (service and Printing with the section "Bed zones"). Install with the machine idle, as in `CLAUDE.md`
      ("Installing and DWC caches"): stop Vision and RS485 first; after installing check `machine.enabledPlugins` and reload every DWC tab.

## 2. Test 1: nothing changes until you turn it on

Goal: installing the feature must not change how the machine behaves.

1. In DWC console: `M140 S40`, then `M105`. **Expected:** only bed 0 heats (the firmware's own behaviour). `M140 S0` turns it off.
2. In the service page, "Workshop services": the process **Bed zones** shows *At rest: the bed zones are off*.
3. The Printing page, section **Bed zones**: the note "The bed zones are off ... only reach bed 0" is shown.

If a second bed heated, the feature is on already: look at `0:/sys/workshop/config/bed-zones.json` (`enabled`).

## 3. Test 2: the board has the four beds

1. In the section: if the board lacks beds, the note says which ones ("The board defines N beds and beds ... are missing").
2. In the console: `M409 K"heat.bedHeaters"`. **Expected:** four numbers, each a heater index (not -1).
3. If a bed is missing, use the assistant (technician): type the sensor and output pin of each zone, check the lines it shows, copy them into `sys/modefff.g`
   (DWC > System files) after the other heater lines, save, **restart the board** (or select the mode again), and repeat step 2.
   The assistant never writes the file and never guesses a pin: check each pin against your wiring BEFORE saving.
4. Tune the PID of every new heater (Printing > PID) before heating anything for long.

**Expected:** the four beds exist and `M105` reports each heater. The note about missing beds disappears.

## 4. Test 3: settings, the copy on the board and the limits

As technician, section Bed zones > Settings:

1. Turn on "Split M140 and M190", keep four zones active, offsets 0, maximum **60**, tolerance 2, timeout **120**. Save. **Expected:** "Saved", the process shows running.
2. Open `0:/sys/workshop/config/bedzones.g` in DWC. **Expected:** it starts with `; bedzones.g -- ... GENERATED by WorkshopService`, `set global.bedZonesMax = 60`
   and one block per zone (`if param.B == 0` ...). Change a zone offset to 2.5 and save: the file changes by itself.
3. Try to save a maximum of 500, a repeated bed number, a layout with fewer cells than zones, an offset over the maximum offset. **Expected:** each is refused with its
   own message under the field and nothing is saved (reload the page: the old values are there).
4. Open the page as an operator. **Expected:** no Settings card; a line says which role is needed. As a viewer: the buttons that heat are disabled; "Turn all off" works.
5. Restart the service (`PluginManager stop` / `start WorkshopService`). **Expected:** `bedzones.g` is the same file (the service writes it again at start only if it differs).

## 5. Test 4: heat and cool from the page

1. Zones 1 to 4 set to offsets 0, 2.5, -3, 0 with zone 4 inactive. Global temperature **40**. Tap **Heat all** once. **Expected:** the button turns amber and says "Tap again"; after 4 seconds
   it goes back by itself. Tap twice: "All zones are going to 40 C".
2. **Expected on the board** (`M105` or the model): zone 1 target 40, zone 2 **42.5**, zone 3 **37**, zone 4 **unchanged** (it is inactive).
3. In the zone 2 row type **45** and tap Set twice. **Expected:** only zone 2 goes to **exactly 45** (no offset).
4. Type **70** in the global field (maximum is 60). **Expected:** the field says "Type from 0 to 60 C" and Heat all is disabled; nothing is sent.
5. Tap **Turn all off** (one tap). **Expected:** every configured zone goes off, **including the inactive one**; the page says so. This button works for every role.

## 6. Test 5: the interception of M140 (the point of the whole feature)

Console, with the feature on and the limits low:

1. `M140 S40` (no P). **Expected:** all active zones get their setpoint plus offset, as in test 4. The console answers "Bed zones: 3 zones set".
2. `M140 P1 S35`. **Expected:** only zone at bed 1, exactly 35, and no message from the service (the code went through untouched). The same for `M140 S35 H3`: a code that names its heaters (slicers such as PrusaSlicer send one per zone) is an explicit order, never spread across the zones.
3. `M140 S0`, then `M140 S-273.15`. **Expected:** every active zone off.
4. `M140 S500`. **Expected:** an error "Zone 0 would go over its maximum ... nothing was sent"; **no heater changes**.
5. `M140 Sabc`. **Expected:** "Invalid bed temperature: abc"; nothing changes.
6. `M140 R40` (a standby code without S). **Expected:** the firmware answers it as usual.
7. Check the service log: one line per intercepted code, no errors, no growing "codes pending".
8. While doing all this, open a second DWC tab and run `M105`, a move or a macro. **Expected:** they run normally: only M140 and M190 are intercepted.

## 7. Test 6: M190 waits for ALL the zones

1. Zones at room temperature. Console: `M190 S35`. **Expected:** the console line stays "busy"; `M105` from a second tab shows the zones rising;
   when **every** zone is within the tolerance of its target the line finishes with "Bed zones: every zone reached its temperature".
2. While that console line waits, a second tab can still run `M105`, jog, or `M140 P2 S20`. **Expected:** they are not blocked.
3. **Timeout.** Set the timeout to 30 s and run `M190 S60` from the cold. **Expected:** after 30 s the line ends with an **error** "zones ... did not reach their temperature in 30 s";
   **the zones keep heating** (the service does not turn them off: do it with Turn all off). Put the timeout back.
4. **The service stops while M190 waits.** Run `M190 S50`, and while it waits stop the service (`PluginManager stop WorkshopService`).
   **Expected:** the console line ends with "WorkshopService is restarting: try again in a few seconds" (or DSF cancels it); the channel is **not** jammed:
   the next console command runs. The heaters **stay at the setpoints they already had**: the firmware keeps controlling them.
   Start the service again and tap Turn all off.
5. `M190 P1 S35` (with P). **Expected:** the firmware's own M190 for that bed; the service does nothing.
6. `M190 S0`. **Expected:** zones off and the line ends at once (it does not wait for a temperature that is not coming).

## 8. Test 7: heater and sensor faults (firmware protection stays)

Only with the heaters OFF and the machine cold, and someone watching.

1. Disconnect the temperature sensor of ONE zone (or use the board's own way to simulate it). **Expected:** the page shows that zone with a red outline and "heater or sensor fault";
   the firmware reports the fault in the console. The other zones keep working.
2. With that sensor still disconnected: `M190 S35`. **Expected:** the line ends with an **error** naming the zone ("heater fault in zones ...") and the other zones are NOT turned off by the service.
3. Reconnect the sensor, clear the fault the usual way (Printing > Status, "Clear fault"). **Expected:** the zone works again.
4. The M143 maximum of each heater stays as the firmware has it: `M143 H<heater>` in the console reports it. Nothing in this feature changes it.

## 9. Test 8: the service is not in the safety loop

1. Heat the zones to 40 with Heat all. Wait until `M105` shows them near 40.
2. Kill the service on the Pi (`PluginManager stop WorkshopService`, or `kill -9` of its `main.py`). **Expected:** the zones **keep** their setpoint and the firmware keeps holding it with its own PID.
   Nothing turns off by itself and nothing runs away.
3. Turn them off from the console with plain `M140 P0 S-273.15` for each bed (or `M140 S0` for bed 0 and the same for the others) **or** with the backup macro (test 9).
4. Start the service again. **Expected:** it comes up, rewrites nothing that differs, and the section shows the current temperatures.

## 10. Test 9: the backup macro without the service

With the service stopped (and Printing's process at rest):

1. `M140 S60` in the console. **Expected:** only bed 0 heats. This is the problem the service solves; it is not a failure.
2. `M98 P"0:/sys/workshop/macros/bedzones-set.g" S40`. **Expected:** the same zones and offsets as test 4 (read from `bedzones.g`), and "Zonas de cama: 3 ajustadas (40 C)" (or the English text).
3. `M98 P"0:/sys/workshop/macros/bedzones-set.g" S45 B1`. **Expected:** only bed 1, exactly 45. The bed is **B**, not P: in `M98` the P is the name of the file, so a `P1` after it is lost and every zone would be set.
4. `M98 P"0:/sys/workshop/macros/bedzones-set.g" S0`. **Expected:** every zone of the settings off, **including the inactive one**.
5. `M98 P"0:/sys/workshop/macros/bedzones-set.g" S70` (maximum 60 in the settings). **Expected:** refused with the maximum of the settings, **nothing sent**.
6. Rename `bedzones.g` to `bedzones.g.off` and run the macro with `S40`. **Expected:** it uses every bed heater of the board, no offsets, and its own fallback maximum (110). Rename it back.
7. Compare with the service: start it, run `M140 S40` from the console, note the targets; run the macro with `S40`: the targets must be identical.
8. The macro never goes around the firmware: with a heater whose M143 limit you set low (for example `M143 H1 S50` with the bed cold, then put it back to its value), `S55` is refused for that bed with "limit of 50 C (M143)".

## 11. Test 10: a real job

1. A slicer start G-code with `M140 S60` then `M190 S60` (no P), then the heating of the hotend. Limits at 60 or above in the settings.
2. Start the job. **Expected:** the zones go to 60 plus their offsets; the job **waits** at `M190` until every zone is within the tolerance, then goes on to the hotend.
3. Repeat and **cancel the job while it waits** at M190. **Expected:** the job stops, the channel is free, and the zones keep whatever your `cancel.g` does with the bed.
   Check that your own cancel macro turns the bed heaters off; this feature does not.
4. Repeat with the plugin Printing stopped from DWC: the job's `M140 S60` reaches only bed 0 and `M190 S60` is the firmware's own (this is the "without the service" case).

## 12. Test 11: the page itself

- [ ] The map shows four squares laid out as the settings say; each has its number, its target and a colour; an alert adds a "!" and a red outline.
- [ ] Select a zone by tapping its square or its row; it highlights in both.
- [ ] The chart shows one line per zone with the same colours as the Status chart; hide / show and the 5 / 10 minute buttons work.
- [ ] Light and dark theme: text readable on every square; the legend bar is visible.
- [ ] A phone-width window (under 600 px) and the kiosk: the map above the table, no horizontal scroll except the preview of the assistant, buttons 44 px high.
- [ ] Spanish and English: no key shown instead of a text; the "?" help of each field opens with four lines.
- [ ] Sign out in the middle of a heating: the page shows the sign-in notice calmly and the heaters stay as they were.

## 13. Differences that are on purpose (not bugs)

- The macro turns **off** with any temperature of 0 or less; the service's `M140 S-5` heats to 0 plus offset. Nobody types a negative temperature.
- Offsets are written to the board with at most 3 decimals; the service sends them as stored. A difference under 0.0005 C is below what a heater can show.
- The macro does not wait for the temperature (use `M116`); the service's M190 does.
- A zone listed in the settings that the board has no heater for is skipped by the macro and shown as "not defined on the board" by the page.
- The service refuses a setpoint over the **maximum of the settings**; the macro and the firmware also refuse at the **M143 limit** of the heater. The stricter one wins.

## 14. If something goes wrong

1. **Turn all off** on the page, or `M140 S0` for each bed, or the macro `S0`, or the power switch. The firmware needs none of this feature to be safe.
2. Turn the feature off: settings > "Split M140 and M190" off > Save. From that moment every M140 / M190 goes to the firmware untouched.
3. If the page cannot load, edit `0:/sys/workshop/config/bed-zones.json` and set `"enabled": false`, or delete the file: the service treats a missing or damaged file as "off".
4. Remove the heater lines the assistant produced: `sys/modefff.g` has dated copies if you made one before saving; restart the board.
5. Write down what happened (the exact console line, the service log lines, `M105`) before changing anything.
